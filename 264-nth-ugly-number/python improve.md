## cur_num not in ugly_set V.S. cur_num not in ugly_nums 這兩種運行速度會有差異嗎?

**會有非常顯著的差異。**

從你的程式碼來看：

| 變數 | 資料型別 | `in` 查詢的時間複雜度 |
|------|---------|---------------------|
| `ugly_set` | `set`（雜湊表） | **O(1)** 平均 |
| `ugly_nums` | `list`（陣列） | **O(n)** |

### 原因

- **`set`** 底層使用雜湊表，查詢某個元素是否存在時，只需計算雜湊值後直接定位，平均 O(1)。
- **`list`** 是線性結構，`not in ugly_nums` 必須**從頭到尾逐一比對**，最壞情況要掃描整個列表，是 O(n)。

### 對這道題的影響

當 `n` 越來越大，`ugly_nums` 會不斷增長。如果你改用 `not in ugly_nums`，每次查詢都會變成 O(n)，整體複雜度會從接近 **O(n log n)** 退化到 **O(n²)**，在 `n = 1690` 時差異會非常明顯。

### 小建議

你目前用 `ugly_set` 來做去重判斷是正確的做法 👍。不過也可以思考看看：這題是否有辦法**完全不需要** `ugly_set`，改用其他方式避免重複？（提示：考慮用三個指標分別追蹤 ×2、×3、×5 的候選值）

## 所以用哈希是其中一種正確的方式, 還能再優化?
沒錯，用 `set` 做去重是**完全正確**的做法，邏輯上沒有問題。

至於優化，可以從兩個方向思考：

### 1. 空間優化
目前你同時維護了 `ugly_nums`（list）、`ugly_set`（set）和 `heap`，佔用較多額外空間。如果能去掉 `set` 和 `heap`，空間會更精簡。

### 2. 時間優化
`heapq.heappush` / `heappop` 每次操作是 **O(log n)**，如果能避免使用堆，整體可以降到 **O(n)**。

### 優化的關鍵思路

想像有三「序列」：

```
×2 序列：1×2, 2×2, 3×2, 4×2, 5×2, ...
×3 序列：1×3, 2×3, 3×3, 4×3, 5×3, ...
×5 序列：1×5, 2×5, 3×5, 4×5, 5×5, ...
```

每個醜數一定是從這三個序列中產生的。如果各用一個**指標**（`i2`, `i3`, `i5`）指向 `ugly_nums` 中對應的位置，每次只要比較 `ugly_nums[i2]*2`、`ugly_nums[i3]*3`、`ugly_nums[i5]*5` 的最小值，就能依序生成醜數，同時**天然避免重複**（當多個序列產生相同值時，指標一起前進即可）。

這樣就不需要 `set` 去重，也不需要 `heap` 排序，時間 O(n)、空間 O(n)。
