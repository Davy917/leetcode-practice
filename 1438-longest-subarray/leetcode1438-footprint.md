### Copilot
先回答你這一點就好：

deque 裡面建議裝「索引 index」，不是差值，也不建議只裝值。

原因很簡單：
1. 你需要知道左邊界移動時，哪個元素已經離開視窗。  
2. 裝索引才能直接判斷「是否出窗」。  
3. 這題通常會有兩個 deque：一個維護目前可能成為最大值的索引，一個維護目前可能成為最小值的索引。  

一句話版本：  
deque 要裝的是「候選最大/最小值元素的索引」。

### User
維護目前可能成為最大值的索引, 這種也不一定要用deque吧, 我第一個版本是直接用#sym:max_num

### Copilot
你說得對，「不一定非要 deque」。  
重點不是資料結構名稱，而是你能不能在滑動視窗中高效維護 max/min。

你第一版用一個 max_num 變數，只有在右邊擴張時很好更新；但左邊收縮時會卡住：

1. 如果被移出去的剛好是目前最大值，max_num 就失效了。  
2. 失效後你只能重新掃整個視窗找新最大值。  
3. 這一步反覆發生，最壞就變 O(n^2)。

deque 的價值在於：
1. 把「可能成為最大值」的候選索引維持成單調結構。  
2. 左邊界移動時，只要看隊首是否出窗，O(1) 丟掉。  
3. 右邊加入新元素時，把不可能再當最大值的尾巴丟掉，攤還也是 O(1)。

所以你的想法不是錯，而是複雜度保證不夠強。  
同樣不是 deque 的做法也可以，例如平衡樹/SortedList/heap+lazy delete，但通常是 O(n log n)，而 deque 可以做到 O(n)。

### User
一開始花了很多時間嘗試, 在拿到這樣一道題時, 我們要怎麼精確判斷現在要使用deque, 而且是兩個deque

### Copilot
你這題的關鍵問題問得很好。  
「要不要用 deque，而且要不要兩個」其實可以用一個很精確的判斷流程。

**快速判斷框架**
1. 題目是不是「連續區間」問題。  
2. 你是不是用滑動視窗在做 left/right 移動。  
3. 視窗合法性是不是依賴極值，像 max - min、最大值、最小值。  
4. 你是不是要在每一步都反覆查極值。  
5. 視窗左邊會刪元素、右邊會加元素。  

以上 5 點都成立，就高度指向「單調 deque」。

**為什麼是兩個 deque**
1. 這題同時需要最大值和最小值。  
2. 一個單調遞減 deque 只能高效給最大值。  
3. 一個單調遞增 deque 只能高效給最小值。  
4. 所以同時要兩端極值時，標準就是兩個 deque。  

**你可以這樣在腦中做資料結構選型**
1. 需要動態 max/min，且有插入與刪除。  
2. 如果只要其中一個極值，用一個單調 deque。  
3. 如果同時要 max 和 min，用兩個單調 deque。  
4. 如果還要中位數、第 k 大這類順序統計，改想平衡樹或有序容器。  

**一句話記憶**
連續視窗 + 每步要極值 + 左刪右加 = 單調 deque；  
同時要最大最小 = 兩個 deque。
